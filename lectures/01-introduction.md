## 1. Требования к инфраструктуре

Слайды 1–4.

Инфраструктуру оценивают по трём последовательным требованиям:

1. Приложение работает.
2. Приложение работает стабильно.
3. Стабильность сохраняется при росте нагрузки.

Успешный запуск на ноутбуке — только начало. Для эксплуатации нужно решить вопросы ресурсов, доставки, безопасности, данных и наблюдаемости.

## 2. От приложения к оркестрации

Слайды 5–10.

Исходная схема: пользователь обращается к приложению, приложение — к базе данных. Для их выполнения нужны серверы с CPU и RAM.

**Образ контейнера** упаковывает приложение, среду выполнения и зависимости. Это помогает воспроизводить окружение при переносе приложения между машинами. В схеме слайда слово `Runtime` обозначает среду выполнения приложения; container runtime как компонент узла Kubernetes рассматривается в лекции 2.

**Оркестратор** управляет запуском множества контейнеров. Kubernetes решает, на каком узле запустить приложение, сколько экземпляров поддерживать, как реагировать на сбои, обновлять приложение и связывать сервисы.

| Объект | Назначение |
| --- | --- |
| Pod | Единица запуска контейнеров в Kubernetes |
| Deployment | Управление экземплярами приложения и их обновлениями |
| Service | Стабильная точка доступа к приложению |
| ConfigMap | Передача обычной конфигурации |
| Secret | Передача чувствительной конфигурации |

Kubernetes работает с **желаемым состоянием**. Например, в описании указано `replicas: 3`; если контролируемых Pod осталось два, контроллер создаёт замену. Пользователь описывает результат, а система постоянно сверяет его с фактическим состоянием.

## 3. Общий кластер и ограниченные ресурсы

Слайды 11–12.

В одном кластере могут работать несколько команд. CPU и RAM конечны, поэтому нужны правила распределения ресурсов.

| Механизм | Что задаёт |
| --- | --- |
| Namespace | Область имён для объектов команды или окружения |
| Requests | Ресурсы, которые учитываются при размещении контейнера |
| Limits | Ограничения потребления ресурсов контейнером |
| ResourceQuota | Совокупные ограничения ресурсов и количества объектов в namespace |
| LimitRange | Значения по умолчанию и допустимые границы ресурсов отдельных объектов |

Namespace помогает организовать общий кластер. Для разграничения доступа и сетевых взаимодействий нужны отдельные политики.

## 4. Права и безопасность

Слайды 13–14.

Основной принцип — выдавать пользователю или приложению только необходимые права.

**RBAC** описывает разрешённые действия над объектами Kubernetes. `Role` задаёт права в namespace, `ClusterRole` может задавать права для ресурсов всего кластера. Права связываются с пользователями и сервисными аккаунтами через bindings.

Безопасность включает четыре вопроса:

- Кто обращается к приложению или API?
- Какие действия ему разрешены?
- Где находятся секреты и кто может их прочитать?
- Какие сетевые соединения разрешены?

Поэтому настройка RBAC — часть общей системы защиты, наряду с управлением секретами и сетевыми ограничениями.

## 5. Данные переживают пересоздание Pod

Слайд 15.

Pod может быть удалён и создан заново. Данные приложения должны сохраняться в постоянном хранилище, если это требуется приложению.

| Объект | Смысл |
| --- | --- |
| PersistentVolume, PV | Ресурс постоянного хранения в кластере |
| PersistentVolumeClaim, PVC | Запрос приложения на постоянное хранилище |
| StorageClass | Класс хранения и параметры выделения томов |

Пересоздание вычислительной части приложения и сохранность его данных — разные задачи. Для базы данных нужно отдельно проектировать хранение и восстановление.

## 6. Конфигурация и доставка изменений

Слайды 16–19.

При росте количества приложений растёт количество манифестов: `deployment.yaml`, `service.yaml`, `ingress.yaml`, конфигурация. Возникает задача переиспользования общих настроек и описания различий между окружениями.

| Инструмент | Подход |
| --- | --- |
| Helm | Шаблоны манифестов и параметры `values` |
| Kustomize | Базовые манифесты `base` и изменения для окружений `overlays` |

Выбор зависит от того, удобнее ли параметризовать шаблоны или изменять общую базовую конфигурацию.

Ручные изменения в production затрудняют ответы на вопросы: кто изменил систему, что именно изменилось и как вернуть предыдущую конфигурацию.

В **GitOps** желаемое состояние хранится в Git. Схема из лекции:

```text
Разработчик → Git → Argo CD → Kubernetes
```

Git даёт историю изменений, а контроллер доставки применяет описание к кластеру и обнаруживает расхождения с ним.

## 7. Инфраструктура данных

Слайды 20–22.

**Workflow** описывает конечный процесс из зависимых шагов. **DAG** — направленный ациклический граф этих зависимостей. Пример из лекции:

```text
Загрузить → Обработать → Проверить → Опубликовать
```

**Kafka** показана как брокер между producer и несколькими consumers. Такая инфраструктура связывает производителей и потребителей событий.

По мере развития платформа объединяет несколько подсистем:

- входящий доступ через Ingress;
- веб-сервисы и workflows;
- Kubernetes как среду выполнения;
- Kafka, storage и Spark для работы с данными;
- GitOps для доставки конфигурации.

Эти подсистемы нужно рассматривать вместе: отказ или ограничение одной части влияет на работу остальных.

## 8. Наблюдаемость и надёжность

Слайды 23–25.

| Источник информации | На какой вопрос отвечает |
| --- | --- |
| Метрики | Что происходит с сервисами и инфраструктурой сейчас? |
| Логи | Какие события и ошибки зафиксировал компонент? |
| Трейсы | Через какие сервисы прошёл запрос и где возникла проблема? |

В схеме лекции Prometheus собирает метрики, на основе которых строятся графики и правила. Логи и трейсы дают контекст сбоя в цепочке сервисов.

Надёжность нужно проверять для разных событий: обновления, падения узла, потери данных и роста нагрузки. Работа системы в обычном режиме ещё не объясняет её поведение при таких событиях.

## 9. Архитектурное мышление

Слайды 26–27.

Инфраструктура объединяет решения в пяти областях: вычисления (`Compute`), безопасность (`Security`), доставка (`Delivery`), данные (`Data`) и эксплуатация (`Operations`).

Порядок обоснования архитектуры:

```text
Проблема → Ограничения → Варианты → Решение
```

Обоснование архитектуры включает описание задачи, ограничений ресурсов и команды, сравнение альтернатив и объяснение выбора подходящего варианта.

Выбор способа развёртывания Kubernetes зависит от доступных серверов, требований к отказоустойчивости, опыта команды и объёма ручной эксплуатации.
