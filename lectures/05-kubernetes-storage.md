## 1. Почему данным нужен отдельный жизненный цикл

Слайды 1-5.

У приложения есть разные категории данных:

- файлы, уже включённые в образ контейнера;
- настройки приложения;
- данные, созданные во время работы;
- резервные копии.

**Pod эфемерен:** его могут удалить, заменить новой репликой или создать заново после сбоя. Новый Pod не получает автоматически файлы из записываемого слоя старого контейнера.

**Volume** подключает хранилище в файловую систему контейнера. В манифесте Pod:

- `spec.volumes` описывает источник тома;
- `volumeMounts` конкретного контейнера задаёт имя тома и путь подключения.

Том может переживать перезапуск контейнера. Сохранность при удалении Pod зависит от типа тома: временный `emptyDir` исчезает, постоянный том имеет отдельный жизненный цикл.

## 2. Общие файлы и временные тома

Слайды 6-8.

Один volume можно подключить к нескольким контейнерам Pod под разными путями:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: shared-volume
spec:
  containers:
    - name: app
      image: nginx:1.27
      volumeMounts:
        - name: shared
          mountPath: /data
    - name: helper
      image: busybox:1.36
      command: ["sleep", "3600"]
      volumeMounts:
        - name: shared
          mountPath: /files
  volumes:
    - name: shared
      emptyDir: {}
```

Файл `/data/report.csv` первого контейнера будет виден второму как `/files/report.csv`. Это один источник данных с двумя точками подключения.

| Тип | Где находятся данные | Что важно |
| --- | --- | --- |
| `emptyDir` | Временное хранилище конкретного Pod | Переживает перезапуск контейнера; удаляется вместе с Pod |
| `hostPath` | Указанный путь на конкретном Node | На другом узле содержимое может отличаться или отсутствовать |

`emptyDir` подходит для временных файлов, кэша и обмена между контейнерами одного Pod. Он не обеспечивает сохранность данных после замены Pod.

`hostPath` даёт контейнеру доступ к файлам узла. В примере лекции это `/var/log`; такой подход нужен прежде всего системным компонентам. Он привязывает приложение к устройству хоста и не создаёт переносимое общее хранилище.

## 3. Настройки приложения как файлы

Слайд 9.

| Механизм | Назначение |
| --- | --- |
| ConfigMap | Обычные настройки приложения |
| Secret | Чувствительные значения: пароли, токены, ключи |
| `projected` | Несколько источников в одном volume |
| `subPath` | Подключение отдельного файла или подкаталога |

Фрагмент `spec.volumes` Pod:

```yaml
volumes:
  - name: config
    projected:
      sources:
        - configMap:
            name: app-config
        - secret:
            name: app-secret
```

Контейнер подключает volume `config`, например в `/etc/app`. Исходные ConfigMap и Secret должны существовать в namespace Pod.

Для ConfigMap и Secret, подключённых через `subPath`, автоматическое обновление содержимого не работает. Доставка нового файла и перечитывание конфигурации самим приложением также являются разными действиями; эта связь разбирается в [лекции о GitOps](06-gitops.md).

## 4. Место хранения и способ доступа

Слайды 10-12.

Два отдельных вопроса:

1. **Где лежат данные?** На диске Node, отдельном сервере хранения или в облаке.
2. **Как они предоставляются приложению?** Как диск, общая файловая система или каталог внутри контейнера.

| Вариант | Как работает | Типичный сценарий |
| --- | --- | --- |
| Блочное хранилище | Узлу предоставляется диск; для файлового доступа на нём используется файловая система | Том данных отдельного приложения или экземпляра БД |
| Общее файловое хранилище | Несколько клиентов обращаются к общей файловой системе | Файлы, доступные Pod на нескольких узлах |

Способности конкретного хранилища определяют, сколько узлов могут подключить том и какие операции разрешены.

Если указывать путь или адрес хранилища прямо в Pod, разработчик должен знать инфраструктуру. Чтобы разделить запрос приложения и устройство хранения, используются PV и PVC.

## 5. PersistentVolume: предоставленный том

Слайды 13-15.

**PersistentVolume (PV)** - объект уровня кластера, описывающий предоставленный том. Он содержит ёмкость, режимы доступа, параметры подключения и политику освобождения. PV существует независимо от конкретного Pod.

Пример статического PV со слайда:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: data-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /mnt/data
```

Это учебный том на файловой системе узла. Сам объект PV не делает `/mnt/data` общим для всех Nodes и не добавляет репликацию.

Для локального диска в лекции отдельно показан `local` PV с привязкой к узлу:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: local-ssd
spec:
  capacity:
    storage: 100Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: local
  local:
    path: /mnt/ssd
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values: [worker-1]
```

`local.path` указывает подготовленный путь, `nodeAffinity` - узел, где доступны данные. Scheduler должен разместить использующий том Pod на подходящем Node. При потере этого узла диск не переезжает автоматически на другой.

## 6. Состояния PV, удаление и finalizers

Слайды 16-18.

| Состояние PV | Значение |
| --- | --- |
| `Available` | Том свободен и может быть связан с PVC |
| `Bound` | Том закреплён за PVC |
| `Released` | PVC удалён, но том ещё не подготовлен к повторному использованию |
| `Failed` | Не удалось выполнить освобождение тома |

Поле `persistentVolumeReclaimPolicy` определяет поведение после освобождения тома:

| Политика | Последствие |
| --- | --- |
| `Retain` | Том и данные сохраняются; дальнейшие действия выполняет администратор |
| `Delete` | Для поддерживающего эту политику хранилища удаляются PV и соответствующий ресурс хранения |

При `Retain` состояние `Released` не означает, что том уже безопасно выдать следующему приложению: на нём могут оставаться прежние данные.

**Finalizer** задерживает окончательное удаление объекта до завершения необходимой обработки. Например, защита PV не позволяет окончательно удалить его, пока он связан с PVC; другие finalizers могут ожидать удаления ресурса хранения.

Если объект долго находится в удалении, нужно проверить события и состояние драйвера. Ручное удаление finalizer обходит защитный механизм, а не устраняет причину незавершённой операции.

## 7. PersistentVolumeClaim: запрос приложения

Слайды 19-23.

**PersistentVolumeClaim (PVC)** - запрос на хранилище в namespace приложения. Он описывает требования, не раскрывая приложению адрес диска или сервера.

Пример PVC для статического PV `data-pv` из раздела 5:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
  namespace: team-a
spec:
  storageClassName: manual
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

`requests.storage` задаёт минимальный требуемый размер. При подборе PV проверяются:

- совпадение класса хранения;
- поддержка требуемых режимов доступа;
- достаточная ёмкость;
- доступность PV: он не связан с другим PVC.

Связь PV и PVC индивидуальная: один PV закрепляется за одним PVC. Если запрос на `10Gi` получил PV ёмкостью `100Gi`, остаток этого PV не раздаётся другим PVC.

| Участник | Что описывает |
| --- | --- |
| Администратор или система provisioning | PV и физическое хранилище |
| Команда приложения | PVC и подключение его к Pod |

```text
Pod -> PVC -> PV -> система хранения
       запрос  описание тома  реальные данные
```

## 8. Режимы доступа

Слайд 24.

| Режим | Сокращение | Смысл |
| --- | --- | --- |
| `ReadWriteOnce` | RWO | Подключение для чтения и записи с одного узла |
| `ReadOnlyMany` | ROX | Подключение для чтения с нескольких узлов |
| `ReadWriteMany` | RWX | Подключение для чтения и записи с нескольких узлов |
| `ReadWriteOncePod` | RWOP | Доступ ограничивается одним Pod во всём кластере |

**RWO ограничивает узел, а не число Pod:** несколько Pod на одном Node могут использовать один RWO-том. RWOP предназначен для ограничения одним Pod и поддерживается CSI-томами при наличии необходимых возможностей драйвера. Режимы доступа также используются при подборе PV и не заменяют файловые права или согласование конкурентной записи в приложении. [Уточнение о режимах доступа](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes).

RWX сам по себе не делает безопасным совместный запуск нескольких экземпляров БД поверх одних файлов данных: это должен поддерживать способ работы приложения.

## 9. Как Pod подключает PVC

Слайды 25-27.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: team-a
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: app-data
```

`volumeMounts.name` связывает точку подключения с записью `volumes.name`, а `claimName` указывает PVC. Pod и PVC должны находиться в одном namespace.

Статическое выделение:

```text
Администратор готовит хранилище и PV
  -> приложение создаёт PVC
  -> Kubernetes связывает PVC с подходящим PV
  -> Pod подключает том через PVC
```

PV существует заранее. Недостатки этого подхода: размеры выбираются до запроса, свободный том может не подойти, каждый новый PV требует подготовки. С ростом числа приложений растёт ручная работа.

## 10. CSI: связь Kubernetes с хранилищем

Слайды 28-30.

**CSI (Container Storage Interface)** - интерфейс интеграции систем хранения с Kubernetes. Конкретный CSI-драйвер устанавливается отдельно и выполняет операции с соответствующей системой: создание и подключение томов, а при поддержке - расширение, снимки и клонирование.

Примеры из лекции:

| Класс хранения | Примеры |
| --- | --- |
| Облачные диски | AWS EBS, Google Persistent Disk, Azure Disk |
| Облачные файловые системы | AWS EFS, Azure Files, Google Filestore |
| Распределённое хранилище | Ceph RBD и CephFS |
| Системы производителей оборудования | CSI-драйвер соответствующего поставщика |

Функции зависят от драйвера. Наличие CSI не означает автоматическую поддержку всех режимов доступа, snapshots или expansion.

Команды просмотра:

```bash
kubectl get csidrivers
kubectl get csinodes
kubectl get pods -A
```

`CSIDriver` показывает зарегистрированные драйверы, `CSINode` - информацию об их доступности на узлах. Дополнительно проверяют состояние Pod компонентов драйвера.

## 11. StorageClass и динамическое выделение

Слайды 31-34, 37.

**StorageClass** - объект уровня кластера с правилами предоставления томов. Он описывает драйвер, параметры хранения, политику удаления, момент provisioning и возможность расширения.

Пример из лекции относится к AWS EBS и требует установленного драйвера и доступа к облачному API:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: ebs.csi.aws.com
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
parameters:
  type: gp3
```

| Поле | Смысл |
| --- | --- |
| `provisioner` | Какой установленный provisioner обслуживает класс |
| `parameters` | Настройки конкретного драйвера |
| `reclaimPolicy` | Политика для создаваемых PV |
| `volumeBindingMode` | Когда выполняются выделение и связывание |
| `allowVolumeExpansion` | Разрешено ли запрашивать увеличение тома |

PVC для этого класса:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
  namespace: team-a
spec:
  storageClassName: fast
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

Это альтернатива статическому PVC из раздела 7. Здесь приложение запрашивает класс `fast`; систему хранения не нужно вручную описывать в Pod.

```text
PVC запрашивает том
  -> StorageClass задаёт способ выделения
  -> CSI-драйвер и контроллеры provisioning создают том и PV
  -> PVC становится Bound
  -> Pod подключает том
```

StorageClass сам не является ни диском, ни работающим драйвером. Объект класса с неверным `provisioner` не сможет обеспечить создание тома.

Выбор класса в PVC:

| `storageClassName` | Поведение |
| --- | --- |
| `fast` | Использовать класс с именем `fast` |
| Поле не задано | Использовать класс по умолчанию, если он настроен |
| `""` | Запрашивать PV без класса; не использовать default StorageClass и его динамическое выделение |

## 12. Когда выделять том: Immediate и WaitForFirstConsumer

Слайды 35-36.

| Режим | Когда происходит выделение или связывание | Следствие |
| --- | --- | --- |
| `Immediate` | После создания PVC | Размещение будущего Pod ещё может быть неизвестно |
| `WaitForFirstConsumer` | Когда появляется использующий PVC Pod и учитывается его размещение | Можно согласовать топологию Pod и хранилища |

Например, диск доступен только в одной зоне. Если создать его заранее, Pod может требоваться другая зона. `WaitForFirstConsumer` позволяет учесть требования Pod перед выбором или созданием тома.

```text
Требования Pod
  -> выбор подходящего размещения
  -> выделение или подбор доступного оттуда тома
  -> подключение и запуск Pod
```

PVC в `Pending` при отсутствии потребляющего Pod может быть нормальным ожиданием в режиме `WaitForFirstConsumer`.

## 13. Диагностика PVC в Pending

Слайд 38.

```bash
kubectl get pvc -n team-a
kubectl describe pvc app-data -n team-a
kubectl get storageclass
kubectl get csidrivers
kubectl get pv
kubectl get pods -n team-a
```

Порядок проверки:

1. Прочитать Events PVC: что именно ожидает или не может выполнить контроллер.
2. Проверить имя и параметры StorageClass.
3. При `WaitForFirstConsumer` проверить наличие Pod и причины, мешающие его размещению.
4. Проверить работоспособность CSI-драйвера и доступ к системе хранения.
5. При статическом выделении проверить свободные PV: класс, размер и access modes.

`Bound` означает, что PVC связан с PV. Это ещё не подтверждение успешного монтирования и работы приложения: дальше проверяются Pod, события подключения и само приложение.

## 14. Расширение, snapshot и clone

Слайды 39-41.

**Расширение** запрашивается увеличением `spec.resources.requests.storage` существующего PVC, например с `10Gi` до `20Gi`:

```yaml
spec:
  resources:
    requests:
      storage: 20Gi
```

Это фрагмент изменения PVC. StorageClass должен разрешать expansion, а драйвер и файловая система - поддерживать операцию. Уменьшение размера PVC таким способом не поддерживается.

**VolumeSnapshot** фиксирует состояние тома на выбранный момент. Пример:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: app-data-snapshot
  namespace: team-a
spec:
  volumeSnapshotClassName: csi-snapshots
  source:
    persistentVolumeClaimName: app-data
```

Для примера нужны установленные компоненты snapshot API, соответствующий класс и поддержка драйвера. Снимок может служить источником нового тома, но не заменяет резервную копию в другом месте.

**Клонирование** создаёт отдельный том из существующего PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data-copy
  namespace: team-a
spec:
  storageClassName: fast
  dataSource:
    name: app-data
    kind: PersistentVolumeClaim
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

Исходный PVC находится в том же namespace. Операцию должен поддерживать драйвер. Получается независимый том, например для тестового окружения; изменения в копии не предназначены для синхронизации с оригиналом.

## 15. Облачное и собственное хранилище

Слайды 42-43.

| Облачное | В собственной инфраструктуре |
| --- | --- |
| Томами управляют через API провайдера | Команда контролирует оборудование и сеть |
| Оборудование обслуживает провайдер | За место, отказы и обслуживание отвечает команда |
| Есть готовые механизмы зон и снимков | Возможности нужно организовать самостоятельно |
| Учитываются стоимость, квоты и зависимость от провайдера | Нужны компетенции по эксплуатации хранения |

Типичный путь развития собственной системы: диски узлов -> общий сервер хранения -> распределённое хранилище на нескольких серверах. Рост отказоустойчивости обычно увеличивает сложность эксплуатации. Один общий сервер сам по себе ещё не устраняет единую точку отказа.

## 16. Базы данных и сохранность данных

Слайд 44.

Постоянный том отделяет данные от жизненного цикла Pod, но не обеспечивает автоматически все свойства надёжной БД.

- База должна восстанавливаться после отказов.
- Локальные диски требуют стратегии отказоустойчивости, например репликации средствами СУБД.
- Оператор автоматизирует типовые операции, но не отменяет необходимость правильно настроить хранение и backup.
- Снимок тома не всегда является согласованной копией базы: нужно учитывать состояние записей и механизм резервирования СУБД.
- Резервную копию проверяют восстановлением, а не только наличием файла или успешным статусом задания.

Основные различия для запоминания:

| Понятие | На какой вопрос отвечает |
| --- | --- |
| Volume | Как подключить источник данных к контейнеру? |
| PV | Какой том предоставлен кластеру? |
| PVC | Какое хранилище требуется приложению? |
| StorageClass | По каким правилам предоставлять тома? |
| CSI-драйвер | Как выполнить операции в конкретной системе хранения? |
| Backup и проверка восстановления | Как вернуть данные после потери или повреждения? |
