# Домашнее задание №2. Сравнение способов развёртывания Kubernetes

[Условие задания](README.md) · [К содержанию курса](../../README.md)

## Область сравнения

**Bare metal** — физические серверы, на которых ОС работает непосредственно с оборудованием. Рассматриваются три способа самостоятельного развёртывания Kubernetes: Hard Way, kubeadm и Kubespray.

**Control plane** управляет кластером и хранит его состояние в etcd. **Worker nodes** запускают приложения. **Bootstrap** — начальная настройка компонентов и подключение узлов к кластеру.

Эти способы автоматизируют разные уровни работы. Kubespray использует kubeadm для создания кластера и добавляет настройку серверов через Ansible. [Kubespray и kubeadm](https://github.com/kubernetes-sigs/kubespray/blob/master/docs/getting_started/comparisons.md).

## 1. Kubernetes The Hard Way

Учебное руководство по ручной настройке компонентов Kubernetes.

| Критерий | Описание |
| --- | --- |
| Развёртывание | Подготовить машины, создать CA и сертификаты, сформировать kubeconfig, настроить etcd, control plane, workers и маршруты между сетями Pod. После этого выполнить проверки работы кластера. |
| Инфраструктура | В руководстве используются четыре физических или виртуальных хоста ARM64/AMD64 с Debian 12: административный jumpbox, один сервер control plane и два workers. Нужны сетевая связность и административный SSH-доступ. Для bare metal используются физические хосты. |
| Автоматически и вручную | Этапы установки выполняет администратор. В руководстве уже есть образцы конфигураций и systemd units; их нужно адаптировать и разместить. После настройки systemd управляет запуском служб, а Kubernetes выполняет свои циклы согласования. |
| Control plane и workers | На сервере запускаются etcd, API Server, Scheduler и Controller Manager как systemd-службы. На workers устанавливаются containerd, runc, CNI-плагины, kubelet и kube-proxy; kubelet подключается к API с подготовленными сертификатами и конфигурацией. |
| Преимущества | Подробное понимание связей компонентов, сертификатов, параметров запуска и сети; полезная база для диагностики. |
| Недостатки и ограничения | Много ручных действий и возможностей ошибиться. Учебная схема имеет один control plane и один etcd, поэтому не обеспечивает HA. Автоматизацию обновлений и масштабирования нужно создавать отдельно. Автор не позиционирует результат как готовый для production. |

Источники: [руководство Hard Way](https://github.com/kelseyhightower/kubernetes-the-hard-way), [требования к машинам](https://github.com/kelseyhightower/kubernetes-the-hard-way/blob/master/docs/01-prerequisites.md), [control plane](https://github.com/kelseyhightower/kubernetes-the-hard-way/blob/master/docs/08-bootstrapping-kubernetes-controllers.md), [workers](https://github.com/kelseyhightower/kubernetes-the-hard-way/blob/master/docs/09-bootstrapping-kubernetes-workers.md).

## 2. kubeadm

Инструмент Kubernetes для начальной настройки кластера и подключения новых узлов.

| Критерий | Описание |
| --- | --- |
| Развёртывание | Подготовить Linux, container runtime, kubelet и kubeadm. Выполнить `kubeadm init` на первом control plane, установить CNI и присоединить остальные узлы. |
| Инфраструктура | Linux-серверы с сетевой связностью, достаточными CPU/RAM и административным доступом. Для HA нужны несколько control plane, etcd с quorum и общий доступный адрес API, например через отказоустойчивый балансировщик. |
| Автоматически и вручную | kubeadm выполняет предварительные проверки, готовит сертификаты, kubeconfig и конфигурацию компонентов, выполняет bootstrap и join. ОС, runtime, сетевой плагин, внешнюю балансировку, постоянное хранение и мониторинг организует команда. |
| Control plane и workers | `kubeadm init` создаёт первый control plane. Дополнительные control plane подключаются через `kubeadm join --control-plane`, workers — через `kubeadm join`. В стандартной схеме компоненты control plane запускаются как static Pods. |
| Преимущества | Меньше ручной настройки, чем в Hard Way; стандартный механизм bootstrap, возможность выбирать компоненты и сохранять контроль над серверами. |
| Недостатки и ограничения | Подготовка машин и значительная часть эксплуатации остаются у команды. Обновления, резервирование, сеть и хранение требуют отдельных процедур. kubeadm можно включить в собственную автоматизацию, но сам он не создаёт физические серверы и не устанавливает на них ОС. |

Источники: [создание кластера с kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/), [отказоустойчивый кластер](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/high-availability/).

## 3. Kubespray

Набор Ansible playbooks для настройки Kubernetes на собственных серверах или в облаке.

| Критерий | Описание |
| --- | --- |
| Развёртывание | Обычно сначала подготовить Linux-серверы. Затем описать их в inventory, выбрать параметры кластера и CNI, запустить `cluster.yml`. Для расширения и обновлений предусмотрены отдельные playbooks. |
| Инфраструктура | Серверы с поддерживаемой ОС и сетевой связностью; управляющая машина с совместимыми Ansible-зависимостями, SSH-доступом и возможностью повышения привилегий на узлах. |
| Автоматически и вручную | Playbooks настраивают системные параметры, runtime, etcd, Kubernetes и выбранный CNI. Администратор подготавливает инфраструктуру, inventory и настройки, организует сетевые правила и запускает нужные процедуры. Внутри для создания кластера используется kubeadm. |
| Control plane и workers | Роли задаются группами `kube_control_plane`, `kube_node` и `etcd`. Один сервер может входить в несколько групп. Playbooks устанавливают компоненты согласно ролям и подключают узлы к кластеру. |
| Преимущества | Повторяемая настройка множества серверов; поддержка bare metal и разных ОС; удобен при уже используемом Ansible. |
| Недостатки и ограничения | Нужно понимать inventory, переменные, совместимость версий и поведение playbooks. Ошибки настройки могут затронуть много узлов. Запуск playbook выполняет процедуру настройки; постоянное управление физическим оборудованием и автоматическое устранение его отказов нужно организовать отдельно. |

Источники: [начало работы](https://github.com/kubernetes-sigs/kubespray/blob/master/docs/getting_started/getting-started.md), [inventory и роли](https://github.com/kubernetes-sigs/kubespray/blob/master/docs/ansible/inventory.md), [область автоматизации и связь с kubeadm](https://github.com/kubernetes-sigs/kubespray/blob/master/docs/getting_started/comparisons.md), [требования и поддерживаемые компоненты](https://github.com/kubernetes-sigs/kubespray).

## Сравнение и выбор

| Подход | Основная область работы | Подходящий сценарий |
| --- | --- | --- |
| Hard Way | Ручная настройка отдельных компонентов | Изучение устройства Kubernetes и его диагностики |
| kubeadm | Bootstrap и присоединение узлов | Свой кластер при готовности команды самостоятельно организовать эксплуатацию |
| Kubespray | Повторяемая настройка ОС и Kubernetes через Ansible | Несколько серверов или кластеров, особенно при опыте работы с Ansible |

Выбор зависит от масштаба и модели эксплуатации. Для обучения наиболее полезен Hard Way. Для самостоятельно обслуживаемого кластера подходит kubeadm, если команда готова организовать подготовку серверов. Kubespray удобен, когда нужна повторяемая настройка множества серверов и есть опыт работы с Ansible.

Отказоустойчивость определяется топологией и эксплуатацией. Для HA типичен control plane из трёх узлов с etcd на них и общим отказоустойчивым адресом API. Число workers определяется нагрузкой. Во всех трёх подходах нужно организовать постоянное хранение, наблюдаемость и резервирование прикладных данных. [Топологии HA](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/high-availability/).

## Короткая заметка об облачных вариантах

- **kOps** создаёт Kubernetes и необходимую инфраструктуру в поддерживаемом облаке, помогает обновлять и масштабировать кластер. Например, поддерживаются AWS и GCE. Это автоматизация собственного кластера в облаке: ответственность за эксплуатацию Kubernetes остаётся у команды. [Документация kOps](https://kops.sigs.k8s.io/).
- **Managed Kubernetes**, например Yandex Managed Service for Kubernetes или Amazon EKS, передаёт обслуживание control plane провайдеру. Способ управления workers зависит от выбранного режима сервиса. Команда выбирает конфигурацию, управляет приложениями, доступом и прикладными данными. Это сокращает объём эксплуатации, но добавляет стоимость облачных ресурсов и ограничения провайдера. [Зоны ответственности Yandex Cloud](https://yandex.cloud/ru/docs/managed-kubernetes/concepts/kubernetes-responsibilities), [Amazon EKS](https://docs.aws.amazon.com/eks/latest/userguide/what-is-eks.html).

Здесь облачные варианты рассматриваются как альтернативы самостоятельному развёртыванию на своих серверах; гибридные режимы с внешними workers требуют отдельного сравнения.
